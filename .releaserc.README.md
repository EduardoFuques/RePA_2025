# Por que semantic-release, y como convive con `.version`

`.releaserc.json` no lleva comentarios porque es JSON estricto. La
explicacion vive aca.

## Que hace

`release.yml` corre `semantic-release` despues de que `ci.yml` pasa en
`main`. Lee los commits desde el ultimo tag y decide si hay version nueva
segun Conventional Commits — que es lo que este repo ya venia usando sin
darle nombre (`feat(be):`, `fix(be):`, `chore:`, `ci:`, `build:`):

| Prefijo del commit      | Efecto en la version |
| ----------------------- | -------------------- |
| `fix(...)`              | patch (1.9.0 -> 1.9.1) |
| `feat(...)`             | minor (1.9.0 -> 1.10.0) |
| `BREAKING CHANGE:` en el cuerpo | major (1.9.0 -> 2.0.0) |
| `chore`, `ci`, `docs`, `test`, `refactor` | ninguno |

Si ningun commit desde el ultimo tag amerita una version, no pasa nada:
no crea tag, no publica imagen, no despliega. Un merge de solo `chore:`
no deberia mover produccion, y no la mueve.

## Los tres plugins, y por que no hay mas

Son los tres que vienen incluidos en el paquete `semantic-release` (por eso
`npx` alcanza y no hace falta `package.json` ni lockfile en un repo que es
Python, no Node). Analizan los commits, escriben las notas y crean el tag +
el GitHub Release. Deliberadamente **no** esta `@semantic-release/git`: no
queremos que el bot pushee commits a `main`.

## De donde arranca la numeracion

El repo no tenia ningun tag. Sin un punto de partida, semantic-release
empieza en `1.0.0` — hacia atras respecto del `1.9.0` que ya declaraba
`.version`. Por eso se sembro el tag `v1.9.0` sobre el commit de `main`
previo a este cambio: la primera version que salga de acá continúa la
numeracion del backend en vez de resetearla.

## `.version` ya no existe

Primero perdio `BACKEND_VERSION`: la imagen del backend se etiqueta con el
tag de git (`vX.Y.Z`) y el servidor la baja de GHCR. Despues `FRONTEND_VERSION`,
que se bumpeaba a mano mientras el frontend se construia en el servidor:
ahora el frontend tiene su propio semantic-release en Repa2025-Frontend y el
servidor baja su imagen (`FRONTEND_REGISTRY_IMAGE`). Que version corre de
cada uno lo dice el `.env` del servidor.
